行为树与上下游的流转架构

六个上游话题、四类事件、一条 100 ms tick 流水线、七级仲裁与一次完整的语音会话生命周期。四张图分别回答：谁把什么送进来、每个 tick 怎么决策、会话怎么推进、事件怎么变成候选。

01 · 总览

上下游总览架构

三个上游引擎通过六个话题进入 behavior_tree_node；节点内部是一条四段流水线；唯一的下游是 /execute_behavior Action Server。终态结果经 /behavior/result_event 回流。

Upstream · 6 topics

两类输入不能互相替代

  • state（1 Hz，BEST_EFFORT）是当前事实：情绪/需求的 triggered、数值、等级，用于执行前的相关性校验。
  • signal_event（RELIABLE）是边沿事件：只在阈值上升沿到达一次，负责创建候选。
  • 感知桥接另走 audio_event（RELIABLE）与 visual_event（BEST_EFFORT，10 Hz 快照）。

Core · 4 stages

内核四段各管一件事

  • IntentMapper 只做语义映射：事件 + 视觉路由 → 带等级的候选，不碰 ROS2 消息。
  • CandidatePool 只做队列：TTL、复合去重键、冷却等待、in-flight 保留。
  • bionic_dog_bt 只做仲裁：七级树、抢占、超时、执行状态机，无 ROS2 依赖。
  • ActionClientAdapter 只做通信：Goal / Feedback / Result / Cancel 的异步适配。

Closed loop

终态只有一个来源

  • Tree 超时或抢占只发 request_cancel + cancel_goal，不伪造 TIMEOUT / CANCELED。
  • 唯一终态是真 Action Result；只有它才释放 in-flight 保留、写冷却、发 result_event。
  • Goal 生命周期：SENDING → RUNNING → CANCEL_REQUESTED → TERMINAL。

02 · 每 100 ms

候选池 → 仲裁 → 执行的一次 tick

上游回调只负责入池；决策全部发生在 tick 里。前四段各做一件事，第五段 ExecuteActiveBehavior 决定这一次 tick 走向三个结果中的哪一个。

CandidatePool

排序、保留与 in-flight 保留

  • 排序键：priority_level ASC → sub_priority ASC → emotion_priority ASC → value DESC → created_at DESC。
  • 未选中的候选留在池里；冷却中的候选等待冷却结束，或等到 TTL 到期被删除。
  • 入池即拒绝：同名已 queued、同名已在 in-flight、去重键重复——去重键是 (source, trigger_event, behavior_name, variant, interaction_mode)。
  • 选中时按 behavior_name + candidate_id 建立 in-flight 保留；被丢弃或未真正派发时立刻释放。

Arbitration

抢占要同时过三道门

  • 等级门：数字越小越优先，低等级直接进入中断策略判定。
  • 同级门：强度差必须 ≥ 15；若属同一 interaction_id，先比 session_preempt_rank（命令 0 < 唤醒定向 10 < 唤醒接近 20）。
  • 中断策略门：immediate / safe_point 放行；non_interruptible、反馈缺失、DISPATCHED、RECOVERY_REQUIRED、safe_to_interrupt=false 一律拒绝。Lv0 emergency_stop 无条件覆盖全部策略。

03 · 语音会话

一次唤醒的会话生命周期

从 EVT_VOICE_WAKEUP 到 CLOSED，会话在四个主阶段之间推进，等待态由两个超时守卫支撑。任一阶段收到新的唤醒事件，旧会话立即作废。

Entry & gating

会话开着时谁能插队

  • 会话活跃期间，Lv0/Lv1 保持正常仲裁；需求和空闲候选等待。情绪阈值事件会保留，待动作资源允许时重新检查状态和目标。
  • 安静的 WAITING 阶段，或具体指令得到真实终态后，可以选择 InPlaceWithHuman 情绪表达；它跳过重复靠近人物，表达动作仍可能使用底盘，Action 前台执行锁会暂停后台 attention 控制。后台跟随与运行中的高等级行为仍会阻止执行。
  • 收到具体指令时执行 consume_turn：暂撤本会话排队的原地情绪；若情绪仍有效，在指令终态后重新解析。运行中的行为范围情绪 Goal 不因语音 idle 被取消。

Fallback

四条兜底都落到 WAITING

  • respond_owner_call 失败 → 直接等待，不再走靠近。
  • 视觉无目标 / 已在一米二内 / 无米制距离（且未开 bbox 兜底）→ 原地等待。
  • 2.0 s 视觉查询窗口超时 → visual_query_timeout。
  • approach_voice_caller 任何终态（含 20 s 超时）→ 回到等待。

Lease

hold 租约与 generation 失效

  • 唤醒即取 hold（lease 6.0 s，每 2.0 s 续约），保证上游不关闭麦克风。
  • 每次阶段跃迁或回合消费都 generation++；迟到的异步结果靠 matches(interaction_id, generation) 被丢弃。
  • EVT_STATE_CHANGED(state=idle) → generation++、释放 hold、discard_session、cancel_current_interaction、关闭 attention。

04 · 四类事件

事件 → 候选的四条映射链

四条来源各有自己的校验与路由规则，但最终都收敛到同一个候选结构。校验是 fail-closed 的：任何字段不匹配就整条事件丢弃，不降级。

Audio · fail-closed

具体指令要同时满足六个字段

  • schema_version=2、event_type 在配置白名单内、should_trigger_behavior_tree=true。
  • dispatch_role=specific_command、command_id 等于配置的 expected_command_id、specific_event_type == event_type。
  • interaction_id / utterance_id 非空，required_voice_slots 存在且取值在 allowed_voice_slot_values 内。
  • TOILET / CLEAN / SLEEP 另需需求闸门：Bladder > 50、Cleanliness > 40、Sleepiness > 50。

Vision routing

三条链各自看什么

  • 需求：只有 Hunger / Social / Exploration 先走视觉路由；其余按 event_type 直接查 event_intent_map。
  • 情绪：check_person 决定 human / solo；语音等待期再分出 voice_waiting，共 18 个语义行为。
  • 视觉：只有 FALL 与 STOP_GESTURE 直接生成候选，且 10 Hz 快照里只在出现沿创建一次。

Level mapping

等级决定默认节奏

  • priority_level 由 behavior_categories.yaml 给出：安全 0、外部交互 1、紧急生理 2、常规生理 3、心理需求 4、情绪表达 5、空闲 6。
  • 默认超时：Lv0 5 s、Lv1 8 s、Lv2 60 s、Lv3/Lv4/Lv5/Lv6 25–30 s；默认冷却：Lv1/Lv5 1 s、Lv3/Lv4 5 s，其余 0。
  • 需求行为例外：Hunger 180 s、Energy 330 s，且 Energy 归入 safety 类别。
