# 优化方向

以下结论来自当前源码调用链。优先级表示建议处理顺序，不代表未经确认就应改变现有产品规则。

## P0：先统一对外契约

### 1. 为 JSON 建立机器可校验协议

现状：所有业务消息都是 String 内 JSON，感知输入不校验 `schema_version`、`timestamp`、字段类型或未知字段；需求/情绪输出也没有正式 JSON Schema。

风险：错误字段会被静默忽略；`event_type` 的数字等值会被转字符串；上下游只能靠文档人工对齐。

建议：为每个话题提供 JSON Schema 或改用自定义 ROS2 msg；在适配器边界统一校验，错误带原因和计数指标。先定义兼容期，再收紧输入，避免突然破坏现有发布方。

### 2. 统一 snake_case 与 camelCase

现状：同一消息混用 `event_type`、`previousLevel`、`triggerThreshold`、`foodType`；只对部分输入字段提供别名。

风险：多语言客户端容易发错，输出端也难生成统一模型。

建议：确定一个 V3 命名标准；V2 保留只读兼容适配，输出只使用一种风格。

### 3. 明确行为结果语义差异

现状：

- `TIMEOUT` 在需求侧按中断减需求，在情绪侧按未满足加 Anxiety。
- Social 的 `Rejected`、`TimedOut`、空 outcome 如果搭配 `COMPLETED`，需求不恢复但情绪按满足处理。
- `ACTION_SLEEP + COMPLETED` 需求不处理，情绪仍按满足处理。
- `FAILED` 不改变需求，但情绪按未满足处理。
- 动作专属 metadata 非法时，需求结算可能失败，但情绪侧只看通用字段，仍可能按 COMPLETED 结算满足。

风险：一个事件在两个系统中表达不同业务结论，行为侧难预测最终状态。

建议：建立 `action_type × result_type × outcome` 的单一结果矩阵，由需求和情绪系统共同引用；明确 TIMEOUT 是中断还是未满足，Social 拒绝不应再复用 COMPLETED 的满足情绪。

### 4. `event_id` 改为必填并定义生命周期

现状：缺少 ID 时不去重；每个系统各自只保留最近 256 个；消息通过结构校验后、进入具体语义分支前就会占用 ID。

风险：重复结算；高频时旧 ID 很快淘汰；若发送方错误复用同一 ID 表示 STARTED 和 COMPLETED，后者会被去重。

建议：要求每个状态事件唯一 ID，另加 `action_instance_id` 关联同一动作生命周期；持久化或按时间 TTL 去重；仅在成功接收对应语义后登记，并输出明确 ACK/拒绝原因。

## P1：补齐已经配置但没有入口的规则

### 5. 接入或删除悬空规则

当前存在但 ROS2 链路未使用：

| 规则 | 现状 |
|---|---|
| Bladder `AfterDrink +20`、`AfterPlay +15` | 核心 API 存在，无订阅调用 |
| `LightsOff → Sleepiness=90` | 核心 API 存在，无输入话题调用 |
| 主人离场 `Social +30` | 有核心方法，但感知入口只能设为在场 |
| Social `responseTimeoutSeconds=30` | 只在配置中 |
| Social `ownerInteractionMergeWindowSeconds=10` | 只在配置中 |
| Fear `freezeThreshold=60` | 只在配置中，不产出冻结信号 |

建议：为每条规则确定权威事件来源和输入字段；若不属于当前版本，移到未来配置或删除，避免调用方误以为已实现。

### 6. 处理动作枚举与行为入口的不一致

现状：23 个 ActionType 只有 13 个在 `actionDemandMap`，其余 10 个的行为结果会被需求、情绪系统共同拒绝，即使它们可能只想影响情绪。

建议：拆成 `knownActions`、`demandActions` 和 `emotionOutcomeActions`；结构校验只验证已知动作，需求系统再按映射筛选，情绪系统按自己的支持表筛选。

### 7. 修正 metadata 别名倍率连乘

现状：`loudnessDb` 与 `loudness_db` 同时存在会乘 1.5 两次；三个主人标识同时为真会乘 1.2 三次。

建议：把别名配置建模为同一字段组，组内 first-present 或 any-match 只应用一次；对重复字段值冲突明确拒绝或规定优先级。

## P1：提高时间与事件可靠性

### 8. 拒绝过期或倒序权威时间

现状：接收端校验 revision 非负，但不要求它单调；也不核对 `virtualTimestamp`、`virtualElapsedSeconds` 与 ISO 时间的一致性。

风险：Transient Local 历史、网络重排或双发布方可能把计算节点重新锚定到旧状态。

建议：按发布者实例 ID、revision、tickSequence 建立单调检查；检测同一话题多权威源；对矛盾时间字段拒绝并报警。

同时应给 `effectiveScale` 增加 `isfinite` 校验；当前实现只检查类型和 `<=0`，NaN/Infinity 可能通过。

### 9. 控制高倍率消息风暴

现状：100 倍时 `/simulation/time_state` 理论 100 Hz，情绪状态也可达 100 Hz；定时器延迟后逐条补发所有虚拟秒。

风险：CPU、DDS 队列和 JSON 序列化压力增大，延迟后补发可能进一步积压。

建议：时间状态按固定真实频率发布并携带权威时间；消费端自行补算。若必须保留逐秒语义，可批量携带 tick 范围，并为状态流和离散事件流采用不同策略。

### 10. 明确 Energy 的时间基准

现状：普通时段按虚拟时间耗电，凌晨特殊加速按真实时间 1 倍耗电。

风险：启用/关闭凌晨加速会让相同虚拟轨迹产生不同电量轨迹；规则虽有测试，但容易被业务方误解。

建议：产品层明确“模拟电量”还是“真实硬件电量”。模拟电量应全程按虚拟时间；真实硬件电量应由硬件输入或全程按真实时间，不宜分时段混用。

## P2：可观测性与数据安全

### 11. 发布拒绝原因和处理指标

现状：大多数非法输入只返回 False 或静默忽略，ROS 回调不记录原因。

建议：增加每话题 accepted/rejected/deduplicated/unknown_event 计数、最近拒绝原因和节流日志；行为结果可发布 ACK 话题。

同时把当前未输出的 `ownerPresent`、`lightsOff`、需求锁定状态等关键上下文放入诊断状态，便于解释数值为何没有变化。

### 12. 避免在状态中原样回显任意 metadata

现状：最近一次情绪事件的完整输入对象会进入 `/emotion/state.lastEmotionEventResult.metadata`。

风险：上游若携带个人标识、大对象或不可信内容，会进入高频状态广播并放大数据量或泄露敏感字段。

建议：白名单保留参与计算的字段，限制深度和大小；调试原文放到可关闭的低频诊断通道。

### 13. 给输出事件增加 ID 和来源

现状：需求/情绪信号没有 `event_id`、source node、因果输入 ID。

建议：增加唯一事件 ID、`caused_by_event_id`、发布节点实例和时间 revision，支持行为组幂等消费及跨节点追踪。

### 14. 区分 dominant 与 triggered

现状：`dominantEmotion` 只取最大数值，不保证越过阈值；同值由固定字典顺序决定。

建议：输出选择规则、并列集合和 `dominantTriggeredEmotion`，或明确 dominant 只用于可视化而非动作决策。

## P2：测试与工程

### 15. 增加真实 ROS2 集成测试

现状：190 项测试覆盖核心逻辑很好，但部分 ROS2 测试通过读取源码文本确认话题/入口，并未实际启动 DDS 图。

建议：增加 launch_testing，验证 QoS 匹配、Transient Local 晚加入、双节点行为结果一致性、高倍率压力、退出清理和消息格式；硬件侧增加录制串口流回放。

### 16. 生成而不是手写重复协议表

现状：配置是权威数值源，但需求、情绪表格和 JSON 模型容易随配置变化而过期。

建议：从配置和 JSON Schema 自动生成事件/阈值附录，并在 CI 中检查本目录生成片段；人工文档只保留业务语义、流程和例外。

### 17. 为配置做启动时完整校验

现状：测试会检查配置，但生产加载只解析文件，没有统一运行时 schema 校验；配置错误可能到特定分支才报错。

建议：节点启动时验证所有阈值顺序、有限数、事件映射、动作映射、时间窗口和恢复值，并给出包含配置路径的错误。

## 建议实施顺序

1. 固化 V2 当前 JSON Schema、行为结果矩阵和错误指标，不先改业务数值。
2. 要求行为结果 `event_id`，拆分动作支持表，补齐悬空入口。
3. 发布 V3 统一命名，提供 V2→V3 兼容适配。
4. 处理倍率别名、时间单调性和高倍率流量。
5. 增加 ROS2 集成测试、硬件流回放和自动文档检查。
