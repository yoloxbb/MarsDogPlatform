# 需求规则

## 基本语义

七个需求均为整数 0..100，写入时自动截断到范围内。数值越大代表需求越强；`Energy` 是“充电需求”而不是剩余电量：

```text
batteryPercent = 100 - Energy
```

自然需求每个虚拟 10 分钟计算一次。除 Energy 外，00:00（含）至 06:00（不含）进入全局锁定；锁定期仅 Sleepiness 继续计算，Energy 始终耗电。

## 默认值与晨起值

| 需求 | 对象刚创建时 | 06:00 晨起重置 | 性格修正 |
|---|---:|---:|---|
| Hunger | 65 | 随机 60..70 | 无 |
| Bladder | 0 | 随机 20..30 | 无 |
| Sleepiness | 15 | 随机 10..15 | 无 |
| Cleanliness | 10 | 随机 5..15 | 无 |
| Energy | 0，即满电 100% | 不重置、不充电 | 无 |
| Social | 20 | `round(随机 20..30 × k_social)` | 有 |
| Exploration | 10 | `round(随机 10..20 × k_curious)` | 有 |

启动时 `MarsdogNeedSystem` 还会显式按 `startupBatteryValue=100` 初始化 Energy。节点虚拟起点恰好为 06:00 时立即执行晨起重置；正常跨过凌晨锁定后也只重置一次。重置会唤醒仍在睡眠中的状态。

## 阈值与等级

当前所有需求比较均为严格大于 `gt`。

| 需求 | NORMAL | TRIGGERED | URGENT | OVERFLOW |
|---|---|---|---|---|
| Hunger | 0..70 | 71..90 | 无 | 91..100 |
| Bladder | 0..75 | 76..100 | 无 | 无 |
| Sleepiness | 0..65 | 66..90 | 无 | 91..100 |
| Cleanliness | 0..70 | 71..100 | 无 | 无 |
| Energy | 0..80 | 81..90 | 无 | 91..100 |
| Social | 0..60 | 61..70 | 71..85 | 86..100 |
| Exploration | 0..60 | 61..100 | 无 | 无 |

未配置 URGENT 或 OVERFLOW 的需求不会自动补齐等级。例如 Bladder=100 仍是 TRIGGERED。

## 自然变化

以下增量均为每个虚拟 10 分钟 Tick：

| 需求 | 时间/条件 | 增量 |
|---|---|---:|
| Hunger | 06:00..21:00 | +1 |
| Hunger | 21:00..06:00 | 0 |
| Bladder | 06:00..21:00 | +3 |
| Bladder | 21:00..06:00 | 0 |
| Sleepiness | 清醒，06:00..21:00 | +4 |
| Sleepiness | 清醒，21:00..00:00 | +5 |
| Sleepiness | 清醒，00:00..06:00 或 `lightsOff=true` | 直接设为 90 |
| Cleanliness | 06:00..21:00 | +2 |
| Cleanliness | 21:00..06:00 | 0 |
| Energy | 任意时段 | 按耗电公式累计 |
| Social | 06:00..18:00 | +2 |
| Social | 18:00..21:00 | +3 |
| Social | 21:00..06:00 | 0 |
| Exploration | 06:00..21:00 且 `Energy < 50` | +5 |
| Exploration | 其他时段或 `Energy >= 50` | 0 |

`Energy < 50` 等价于硬件电量严格大于 50%；电量恰好 50% 不增长 Exploration。

Energy 默认满电续航 120 分钟。按秒数计算：

```text
精确增量 = 上次小数余量 + 100 × elapsedSeconds / 7200
本次整数增量 = floor(精确增量)
新 Energy = clamp(旧 Energy + 本次整数增量, 0, 100)
新余量 = 精确增量 - 本次整数增量
```

普通需求 Tick 的 `elapsedSeconds` 为 600，因此 12 个 Tick 恰好从 Energy=0 到 100，轨迹是 8、16、25、33、41、50、58、66、75、83、91、100。凌晨特殊加速改按每步分摊的真实时长耗电，详见[时间规则](时间规则.md)。

## 各需求业务规则

### Hunger

进食恢复公式：

```text
recovery = round(foodRecovery × eatEfficiency × max(0, portions))
Hunger = clamp(Hunger - recovery)
```

| 食物 | 单份恢复 |
|---|---:|
| PremiumFood | 30 |
| NormalFood | 20 |
| Snack | 5 |

| 效率 | 系数 |
|---|---:|
| Full | 1.0 |
| HalfInterrupted | 0.5 |

每次完成进食还会按“进食前 Hunger”联动 Bladder，并让 Cleanliness +20：

- 进食前 Hunger > 90：Bladder +25。
- 否则进食前 Hunger > 70：Bladder +20。
- 否则 Bladder 不变。

### Bladder

- `ACTION_DEFECATE + COMPLETED`：直接归零。
- 中断专用变化为 -40，覆盖全局 -20。
- 配置还定义 `AfterDrink +20`、`AfterPlay +15`，核心方法可以调用，但当前没有 ROS2 话题入口调用它们。

### Sleepiness

触发入睡前同时要求：

1. Sleepiness > 65。
2. 当前已在睡眠；或处于强制睡眠条件；或处于 06:00..00:00 且不在 06:00..08:00 强制清醒窗口。

因此 Sleepiness 足够高时：07:00 不允许新入睡，12:00、22:00、02:00 允许。`ACTION_SLEEP + STARTED` 才真正进入睡眠，初始状态为 Shallow，剩余 14 个 Tick。需要注意，收到 STARTED 后的执行方法不会再次校验 `sleepActionAllowed`，所以行为组必须在发送前遵守触发条件。

浅睡每 Tick：

- Sleepiness -2。
- 睡眠时长 +10 分钟。
- 第 14 个 Tick 后，若 Sleepiness 仍 >65 或仍处于强制睡眠，进入 Deep；否则醒来。

深睡每 Tick：

- Sleepiness -15。
- 睡眠时长 +10 分钟。
- Sleepiness <=20 且不处于强制睡眠时醒来。

`INTERRUPTED`、`CANCELLED`、`TIMEOUT` 会先唤醒，再将 Sleepiness -20。晨起重置也会唤醒。

### Cleanliness

- 每次完成进食：+20。
- `ACTION_GROOM + COMPLETED`：-50。
- 中断/取消/超时：-20。

变量名是 Cleanliness，但数值实际表示脏污/清洁需求；数值越高越需要清洁。

### Energy

- `ACTION_RECHARGE + COMPLETED`：读取回传的电池百分比 `B`，写入 `Energy=100-B`。
- 未回传电量时目标电量为 100%，即 Energy=0。
- 外部设置电量、充电或中断后都会清空之前的小数耗电余量。
- 中断/取消/超时：Energy -20，即减少充电需求；这是当前源码的实际效果。

### Social

主人状态从“非明确离场”变成离场时 Social +30；连续重复离场不再增加，重新在场后下一次离场才会再加。当前 ROS 感知入口只能把主人设为在场，不能触发离场。

Social 动作完成恢复：

| `socialOutcome` | Social 变化 |
|---|---:|
| `OwnerInteraction` | -25 |
| `DogHumanResponded` | -20 |
| `DogAnimalResponded` | -15 |
| `Rejected` | 0，但消息视为已成功处理 |
| `TimedOut` | 0，但消息视为已成功处理 |
| 空或缺失 | 0，但消息视为已成功处理 |
| 其他值 | 拒绝结算 |

前三种无恢复结果只要当前 Social 仍激活，就可能触发 `ACTION_RESULT_STILL_ACTIVE` 同级需求信号重发。

配置中的 `responseTimeoutSeconds=30` 和 `ownerInteractionMergeWindowSeconds=10` 当前未被执行逻辑读取。

### Exploration

三类探索动作只要 `COMPLETED`，统一将 Exploration -15；metadata 和传入的探索结果类型都被忽略。

## 最紧急需求

核心 API 只让已经越过首次触发线的需求参与，然后按原始 `value` 从大到小选一个。它不按“超出各自阈值多少”归一化；同值时按字符串名称倒序的排序结果决定。
