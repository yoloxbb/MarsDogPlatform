# MarsDog 五人团队开发规范

新功能以一条可验收的机器人场景组织，源码按现有模块维护。每个功能指定一个交付负责人；模块 owner 对所属实现和公开边界负责。角色见 [责任表](../OWNERSHIP.md)，新功能先填写 [功能规格](templates/FEATURE_SPEC.md)。

## 从需求到合并

1. 功能负责人说明触发、目标、前置条件、结束方式、失败行为和验收环境。标记是否改变已有机器人行为或内部状态规则。
2. 对照 [能力基线](../architecture/CAPABILITY_BASELINE.md) 判断需要复用、补齐还是新增能力。分别列出涉及的 Voice 事件、BT 行为、Action Unit 和导航服务。
3. 接口生产方与消费方确认字段及语义。跨模块功能在一个可评审变更中提交实现、配置、契约与说明；较大功能拆成可独立回归的兼容切片。
4. 在所属独立环境开发。新行为先写预期和关键回归，再实现；日常工程选择由实现者处理。
5. 按 [测试矩阵](WORKFLOW.md#按变更选择门禁) 执行检查。功能负责人汇总整条链路证据，跳过、失败及替身范围分别记录。
6. 使用 PR 模板提交，列出功能负责人、受影响模块评审人、实际测试和部署变化。真实账号与仓库审查规则由团队绑定。
7. 集成负责人记录用于板端验证的源码、配置、依赖和 overlay。板端测试通过后，再将对应环境的能力状态升级。

## Python 与模块结构

- 核心业务、外部能力适配和 ROS 装配各有明确职责；按模块需要组织，不强迫历史代码一次性换目录。
- 新组件显式接收依赖。为外部协作者声明小型 `Protocol` 或可替换接口，领域输入输出使用有类型的数据对象；不向新的业务组件传整个 Node。
- 明确每项可变状态的 owner、锁和生命周期。回调使用会话、目标或代次标识拒绝迟到结果；取消后仍需处理在途回调。
- ROS 回调中的耗时推理、等待和 I/O 必须有明确执行上下文、并发限制、超时和退出路径。异步函数中使用阻塞等待时说明执行线程和影响。
- 单元测试注入时钟和外部协作者，验证领域行为及故障路径。不要为便于测试复制第二套业务实现。
- 新增或修改的公开函数写清输入、返回、异常和单位；边界处校验类型、有限数值、枚举及必要字段。
- 沿用模块现有代码风格，新增命名使用 Python 常规命名；旧标识按 [命名目录](../../interfaces/naming/README.md) 兼容。格式化、算法升级和依赖升级分别评审。
- 各模块保留自己的 pyproject、lock 和环境。公共包只承载已确认的基础设施，不放跨领域决策和可变 RobotState。

## 接口与数据规则

每个新增或变更接口记录以下内容，并更新 [接口登记](../../interfaces/registry.json) 与对应协议说明：

| 项目 | 必须回答的问题 |
| --- | --- |
| 所有权 | 谁生产、谁消费、谁评审变更？ |
| 身份 | 如何关联 interaction、utterance、target、epoch、Goal？哪些字段仅本领域有效？ |
| 时间 | 时间戳来自哪个时钟？有效期从采样、接收还是执行起算？重启或时钟回退如何处理？ |
| 空间与单位 | 坐标系、图像尺寸、像素变换、距离和角度单位是什么？ |
| 状态 | 接受、执行中、完成、失败、取消和未知结果如何区分？ |
| 异常 | 错误码、超时、重试、重复请求、迟到回复和恢复条件是什么？ |
| 传输 | Topic / Service / Action、类型、QoS、版本兼容方式是什么？ |

现有 JSON envelope 的容错行为属于兼容契约，不能直接换成更严格的统一解析器。新增版本可设计明确 schema，并用生产方与消费方的固定样例验证。导航当前复用 VoiceTask 是历史边界，独立类型迁移列为后续兼容变更。

## 配置和能力

同一规则有一个运行时权威来源。模块配置属于对应 owner；平台 profile 负责装配与显式覆盖，生成的能力目录用于检查，不成为新的运行时配置源。

功能是否可交付同时记录四个维度：配置引用是否完整、逻辑及通信验证范围、指定板端环境是否可运行、指定实机场景是否验收。不能用模板存在、模型已安装、测试替身成功中的任意一项代替其他维度。

新的场景优先组合已有能力。普通行为通过既有声明配置扩展；有独立状态、超时与恢复过程的交互使用明确的流程组件。新增特例必须写清归属，并在功能规格中说明为什么现有扩展点不适用。

## 测试与日志

| 层次 | 核心证据 | 不代表什么 |
| --- | --- | --- |
| 领域单测 | 决策、状态、阶段、取消及错误分支 | 不代表 ROS 通信或硬件通过 |
| 契约和 DDS | 生产消费语义、真实传输、重启与终态归属 | 替身感知、模拟导航仍是替身 |
| ARM64 安装运行 | 当前源码安装来源、依赖、overlay、回放与资源记录 | 不代表真实运动或模型质量 |
| 实机场景 | 指定设备、配置、场地、输入和停止证据 | 不自动外推到其他型号或场景 |

测试只使用隔离配置，不接入生产 ROS domain。涉及硬件的测试必须另行安排；不能把默认 launch 用作接口探测。已有冻结契约只读，修复实现或明确版本迁移，不能自动重采样消除失败。

复用统一日志记录 run、component、会话、目标、Goal、阶段、错误码和实际配置。记录选择原因、拒绝原因、取消请求、终态及恢复锁；密钥、原始私人音视频和无界高频内容不进入普通日志。

板端性能先测量再确定门限：端到端延迟、感知数据年龄、队列积压、取消至停止确认时间、CPU/内存/NPU 使用。计时必须说明起止点、样本数量和运行配置，不把单元测试耗时当作实机性能。

## 完成定义

功能规格与实际行为一致；生产消费双方认可契约；所选门禁有完整结果；未验证范围明确；配置和版本可复现；可以说明取消、失败和恢复行为。产品能力状态只升级到证据覆盖的范围。跨模块功能由功能负责人确认完成，发布由当期集成负责人确认版本组合。
