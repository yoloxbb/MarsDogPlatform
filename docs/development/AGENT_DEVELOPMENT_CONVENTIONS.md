# MarsDog 开发公共约定（Agent 精简版）

版本：2026-10-14。供各模块 Agent 开工前阅读，仅包含公共命名与 Git 协作约定。

具体架构、接口字段、仲裁、会话、导航及设备细节，在任务涉及时查阅所属模块文档，不要求每次加载整份架构手册。仍须遵循当前仓库适用的 `AGENTS.md` 和用户明确要求。

## 1. 命名规范

### 1.1 新增名称

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| Python 文件、模块、函数、变量 | `snake_case`，表达具体职责 | `target_cache.py`、`get_target` |
| Python 类 | `PascalCase` | `TargetCache` |
| Python 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_TIMEOUT_SEC` |
| ROS 包 | 小写字母、数字、下划线，明确领域 | `marsdog_interfaces` |
| ROS 节点 | 小写下划线，表达节点职责 | 沿用所属模块约定；统一 `*_node` 后缀仍是待评审建议 |
| ROS 消息、服务、Action 类型 | `UpperCamelCase` | `VisionTask`、`ExecuteBehavior` |
| Topic / Service / Action 端点 | 延续所属领域路径、小写下划线 | `/perception/voice/task` |
| 事件 / 信号 ID | 沿用所属领域族，大写下划线 | `EVT_VOICE_*`、`EVT_VISION_*`、`NEED_*`、`EMO_*` |
| 命令 ID | `CMD_*` | `CMD_HAND` |
| 新意图 / 新行为 ID | 小写下划线，表达选择入口或行为任务 | `command_handshake`、`give_paw` |
| 动作单元 ID | `ACT_` + 大写下划线 | `ACT_INTERACT_GIVE_PAW` |
| 带量纲参数 | 明确单位，沿用所属协议 | `timeout_sec`、`stand_off_distance_m` |

### 1.2 兼容与可读性

- 优先复用现有准确名称，不另造同义名称；避免 `data2`、`new_handler`、`temp_manager` 等无法说明职责的名字。
- 上表约束新增名称，不要求批量重命名历史代码。已有公开字段、类型、端点、行为 ID 保持兼容。
- 历史 `expressJoyAlone`、`ACT_SPLoot_LIE_DOWN` 等保留精确拼写；兼容例外按仓库登记维护，不自动转换大小写。
- 事件、命令、意图、行为和 Unit 是不同对象。通过显式映射关联，不凭同名前缀推导关系。
- Voice 产品动作标签不是 Action 的 Unit ID；VoiceTask 与 VisionTask 即使字段相同，也不是同一 ROS 类型。
- 文件整理、格式化与功能变更分别说明，避免在一个修复中夹带大规模改名。
- 新的端点层级、统一节点后缀及机器人 namespace 策略尚需团队确认，不能将建议名称当作已部署接口。

涉及公开名称或跨配置引用时，查阅仓库的 `interfaces/naming/README.md`、`interfaces/naming/compatibility_exceptions.json` 和 `interfaces/registry.json`。

## 2. Git 与协作约定

### 2.1 开工与修改范围

1. 先查看工作区状态、当前分支及已有修改，明确本任务涉及的模块和文件。
2. 保留其他开发者或 Agent 的工作；不覆盖、回退或清理无关修改。遇到同一文件并发修改，先核对差异再继续。
3. 在所属模块及任务授权范围内修改。跨模块访问走公开接口，不通过私有 import 绕过边界。
4. 接口变更同时核对生产者、消费者、配置和测试，不能只让本模块单独通过。
5. 普通兼容修复在已有授权内推进；未获授权的不兼容变更或产品行为变化，按仓库规则提供具体影响和可评审方案。已经确认的事项不重复申请。

### 2.2 分支与提交

**以下分支及提交格式为团队统一方案建议；仓库已有明确约定时沿用已有约定，尚未批准时不据此改写历史。**

- 从仓库实际主干建立短期分支，主干名称以仓库为准。
- 分支示例：`feat/vision-target-cache`、`fix/voice-session-timeout`、`refactor/action-lifecycle`。
- 一次提交围绕一个明确目的；一个跨模块功能可放在同一 PR，较大改动拆成可独立验证的部分。
- 提交说明建议使用 `类型(模块): 具体变化`，例如：

```text
feat(vision): 增加目标观测查询
fix(voice): 忽略旧会话的迟到识别结果
refactor(action): 拆分执行协调与状态访问
docs(behavior): 补充候选仲裁说明
```

不提交凭据、设备私有配置、虚拟环境、构建产物或未经项目规则管理的大型模型文件。提交前检查 diff，不把其他人的修改一起提交，不使用无差别暂存代替审阅。

### 2.3 验证与评审

- 按变更执行必要检查，入口见 `docs/development/WORKFLOW.md`。单模块改动优先验证受影响模块；涉及公共接口时补生产消费契约和相应集成验证。
- 纯文档变更检查内容、路径和格式，不为其启动无关硬件测试。
- 实际通过、失败、跳过、未运行分别报告；模拟与软件测试不表述为实机验收。
- PR 说明写清问题、结果、兼容影响和实际验证。不要仅写“优化代码”“修复问题”。
- 跨模块契约由相关生产消费方共同评审。至少一名非作者技术评审及远端分支保护属于建议安排，以团队实际批准和配置为准。
- 合并、推送与部署遵循当前任务授权和仓库流程；代码合并本身不表示设备已部署或产品已验收。

### 2.4 Agent 最小交付说明

```text
结果：解决的问题与修改后的行为。
范围：修改的模块、主要文件及接口影响。
验证：实际执行的检查、结果、未运行或跳过的原因。
剩余：未完成项、依赖条件；如需部署，写明配置和回滚影响。
```

公共约定维护一份。各模块专属说明仅补充本模块的入口、依赖、测试与特殊约束；涉及其他领域时按需阅读对应协议，不复制整套架构文档后分别维护。
